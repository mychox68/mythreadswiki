# 가재코드(Gajae-Code) — 뭘 하는 도구고, 설치해도 되나

> [!question] 질문
> 가재코드를 설치해서 Claude Code와 Codex 둘 다에서 쓰고 싶다. 설치 전에 특별히 문제 되는 부분이 있는지 확인하고, 뭘 하는 도구인지 정리해달라.

## 결론 (TL;DR)

- **설치 자체의 기술적 위험은 낮다.** npm 패키지(`gajae-code`, `@gajae-code/coding-agent`) 모두 **postinstall/preinstall 스크립트 없음**을 확인했고, 공식 `install.sh`도 `sudo` 없이 `~/.local/bin`에만 파일을 두는 사용자 수준 설치다. 사용자 CLAUDE.md의 npm 공급망 공격 경고(Mini Shai-Hulud)와 직접 겹치는 postinstall 훅 벡터는 없다.
- 다만 **"Claude Code랑 Codex에 다 깐다"는 표현은 정확하지 않다.** 가재코드는 OMC 같은 **플러그인이 아니라 독립 실행 바이너리(`gjc`)**다. Claude Code/Codex 내부에 설치되는 게 아니라, 그 밖에서 별도 프로세스로 떠서 Claude Code CLI·Codex CLI·Gemini 등을 **백엔드 프로바이더로 호출**하는 구조다. 그래서 "한꺼번에 깐다"기보다는 "가재코드 하나를 깔고, 그 안에서 여러 모델/CLI를 골라 쓴다"가 더 정확한 그림이다.
- **베타/실험 단계임을 README가 명시** — "expect rough edges, verify outputs before relying on it for important work". 6주 만에 릴리스 55개가 나올 정도로 **변경 속도가 매우 빠름** (2026-05-26 생성 → 2026-07-14 기준 v0.10.2). 안정성보다 기능 추가 속도가 앞서는 시기로 보임.
- 구독형 플랜(클로드 Pro/Max, ChatGPT Plus 등)을 외부 CLI에서 호출하는 게 약관상 회색지대일 수 있다는 우려가 커뮤니티에서 나왔으나, 이건 가재코드만의 문제가 아니라 **모든 서드파티 하네스(레이지코덱스, OMC 등)에 공통되는 이슈**이고 볼트에서 명확한 결론은 못 찾음 (아래 "열린 질문" 참고).

## 설치 방법

- 전역 설치(권장 경로): `bun install -g gajae-code` — 이 npm 패키지는 실제로는 `@gajae-code/coding-agent`를 설치하는 원-라인 래퍼.
- 순수 npm으로도 설치 가능: `@gajae-code/coding-agent` 스코프 패키지 직접 설치.
- 플랫폼별 프리빌드 바이너리 제공: Linux(x64/arm64), Windows(x64), macOS(arm64/x64).
- 공식 설치 스크립트: `curl -fsSL https://raw.githubusercontent.com/Yeachan-Heo/gajae-code/main/scripts/install.sh | sh` (macOS Intel 등에서 소스 빌드가 필요하면 `-- --source` 옵션).

## Claude Code / Codex와의 관계 — "패키지로 깔리는" 게 아니다

**oh-my-codex, oh-my-claudecode(OMC)와 가재코드는 설치되는 층위 자체가 다르다.**

| | oh-my-codex / oh-my-claudecode(OMC) | 가재코드(`gjc`) |
|---|---|---|
| 정체 | Codex CLI / Claude Code CLI **안에 얹는 플러그인** | **독립 실행 프로그램** (omp를 하드포크한 자체 에이전트 코어) |
| 설치 위치 | 이미 설치된 Codex/Claude Code의 확장 슬롯(`.codex/`, `.claude/` 등)에 들어감 | 완전히 별도의 전역 명령어로 설치(`bun install -g gajae-code`) |
| 전제조건 | **Codex나 Claude Code가 먼저 설치돼 있어야 함** — 그 위에서만 동작 | Claude Code·Codex가 없어도 그 자체로 완결 동작 |
| 실행 방법 | `claude`나 `codex` 명령어를 쓰면 그 안에서 로드됨 | `gjc`라는 **별도 명령어**로 따로 실행 |
| 모델 연결 | 호스트(Claude Code/Codex)의 인증을 그대로 씀 | 자체 프로바이더 설정(`~/.gjc/config.yml`)으로 Anthropic/OpenAI/Google/xAI API에 직접 연결 (omp와 동일한 구조) |

가재코드 README 원문이 이걸 명시적으로 못박고 있다.

> *"It is intentionally not a hidden plugin for Codex CLI, Claude Code, OpenCode, or Claw Code."*
> (Codex CLI, Claude Code, OpenCode, Claw Code를 위한 숨은 플러그인이 **의도적으로 아니다**.)

즉 가재코드는 `claude`나 `codex` 바이너리를 내부적으로 서브프로세스로 호출해서 "불러 쓰는" 구조가 아니라, omp와 마찬가지로 **자체 모델 연결을 가진 완결형 에이전트**다. `claude`/`codex`와 나란히 서는 독자적인 세 번째 명령어로 보는 게 정확하다.

카톡방 사례에서 나온 "가재도 클로드처럼 `gjc -p`로 요청하면 해줄 것"이라는 언급은, **가재코드가 claude/codex를 호출한다는 뜻이 아니라 가재코드 자신도 `claude -p`처럼 비대화형(programmatic) 모드를 지원해서, 다른 도구(헤르메스 등)가 가재코드를 프로그램적으로 호출할 때 이 방식을 쓴다는 뜻**이다(참고: [[2026-07-09 hermes 하네스-삼국지-오르카-가재코드-omp]]). "기획은 Fable, 코딩은 Codex, 테스트는 Opus"처럼 역할별로 다른 도구를 섞어 쓰는 건 가재코드 하나의 기능이 아니라, 사용자가 여러 독립 CLI(가재코드 포함)를 **수동으로 나란히 오케스트레이션**하는 사용 패턴에 가깝다.

정리하면 설치 그림은 "Claude Code CLI, Codex CLI, 가재코드(`gjc`)가 각자 독립적으로 설치된 세 개의 명령어로 공존하고, 필요할 때 사용자가 상황에 맞게 골라 쓴다"이다. OMC처럼 `.claude/` 안에 스킬·에이전트 파일을 심는 "패키지 설치" 방식과는 설치 지점 자체가 다르다.

## omp(Oh My Pi)와의 관계 — 계보 확인

카톡방 노트([[2026-07-09 hermes 하네스-삼국지-오르카-가재코드-omp]])의 요약에 "가재코드(GJC)는 omp 하드포크"라는 표현이 있었는데, 원문 대화만으로는 근거가 약해 보여 가재코드 저장소 자체의 `NOTICE.md`를 직접 확인해 검증했다.

- **계층상 같은 레벨**: [[20260712-233546-orca-가이드]]에서 정리한 "에이전트 코어 vs 오케스트레이션 IDE" 구분을 적용하면, 가재코드는 Orca(오케스트레이션 계층, 자체 에이전트 없이 남의 CLI를 관제만 함)가 아니라 **omp·Claude Code·OpenCode와 같은 "에이전트 코어" 계층**이다 — 자체 런타임·도구 시스템·TUI를 가진 독립 CLI라는 점에서 동급.
- **단순 동급이 아니라 실제 계보 관계**: 가재코드 저장소의 `NOTICE.md`는 [[20260712-233506-omp-oh-my-pi-가이드]]에서 다룬 **oh-my-pi(omp)를 "upstream red-claw lineage and implementation DNA"**라고 명시한다. 즉 제작자 본인이 가재코드 구현의 뿌리가 omp임을 인정한 것 — 카톡방의 "하드포크" 주장이 근거 있는 얘기였음이 1차 자료로 확인됨.
- 단, GitHub API 상 `fork: false` — GitHub의 공식 Fork 버튼으로 연결된 게 아니라, omp의 코드/구현을 가져와 **독립 저장소로 새로 시작한 커뮤니티적 의미의 "하드포크"**다.
- `NOTICE.md`에 함께 언급된 계보: `oh-my-codex`(Codex 중심 오케스트레이션 실험), `oh-my-claudecode`(제작자 본인의 이전 작품, OMC), `insane-search`(MIT 라이선스 공개 fetch 엔진).
- 종합하면: **가재코드 = omp의 코드베이스/구현을 뿌리로 삼되, 그 위에 OMC식 4-스킬 워크플로(deep-interview/ralplan/ultragoal/team)와 Windows 크로스플랫폼 지원(brush-bash 이식), 알림 SDK 등 제작자 본인의 색깔을 얹어 재구성한 파생 프로젝트**. omp가 원본에 가깝고, 가재코드는 그 위에 얹힌 갈래로 이해하면 된다.

## 이전 조사와의 차이 (2026-07-05 → 현재)

[[20260705-112912-gajae-code-omc-비교]]에서는 "OMC가 무거워서 나온 가벼운 대안, 갈아탈 필요는 없다"는 결론이었다. 그 사이 열흘간 star가 1.5k→1.9k로 늘고 버전도 계속 올라갔지만, **"OMC와 대체 관계가 아니라 성격이 다른 독립 도구"라는 핵심 결론은 그대로 유효**하다. 이번 조사에서 새로 확인된 건 설치 자체의 안전성(postinstall 훅 없음)과 Claude Code/Codex와의 관계가 "플러그인 설치"가 아니라 "별도 오케스트레이터가 CLI들을 호출하는 구조"라는 점.

## 열린 질문 (설치 전 사용자가 직접 확인하면 좋음)

1. **구독형 플랜 ToS 문제**: Claude Pro/Max, ChatGPT Plus 같은 구독을 가재코드가 백엔드로 호출할 때 각 사의 이용약관(자동화·서드파티 클라이언트 제한)에 저촉되는지 여부. 볼트/저장소 문서 어디서도 명확한 답을 못 찾음 — 계정 정지 리스크가 걱정되면 API 키 기반 사용으로 한정하는 게 안전.
2. **npm 발행자 `bellman_04`의 신원**: 저장소 소유자(Yeachan-Heo)와 관계가 명확히 문서화된 걸 찾지 못함. 대부분의 오픈소스 프로젝트에서 흔한 팀 배포 계정일 가능성이 높지만, 확신이 필요하면 저장소 `package.json`의 `publishConfig`/`CONTRIBUTING.md`나 Yeachan-Heo 본인 소셜 계정에서 직접 언급을 확인.
3. **`computer-use`(데스크톱 제어)**: 저장소 스스로 "실험적"이라 명시. 이 기능을 켜면 로컬 데스크톱을 에이전트가 직접 조작하게 되므로, 처음 설치 시엔 이 기능은 끈 채로 시작하고 필요할 때만 별도로 검토하는 걸 권장.

## 설치 판단 요약

- 기술적 설치 위험(공급망 공격 벡터)은 낮음 — 진행해도 무방.
- 다만 베타 단계 + 빠른 변경 속도이므로, **중요한 실무 작업에 바로 전면 투입하기보다 사이드로 먼저 써보며 검증**하는 접근을 권장(이전 조사 [[20260705-112912-gajae-code-omc-비교]]와 동일한 권고).
- `computer-use`, 알림 데몬(Telegram/Discord/Slack) 등 권한 범위가 넓어지는 옵션 기능은 필요한 것만 선택적으로 켤 것.
- 구독형 플랜 연동 시 ToS 리스크는 사용자가 각 서비스 약관을 직접 한 번 더 확인하는 걸 권장 (본 조사에서 명확한 결론 없음).
