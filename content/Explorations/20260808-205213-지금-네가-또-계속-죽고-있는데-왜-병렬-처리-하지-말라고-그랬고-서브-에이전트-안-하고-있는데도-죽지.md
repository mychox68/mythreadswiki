# 지금 네가 또 계속 죽고 있는데,, 왜 병렬 처리 하지 말라고 그랬고 서브 에이전트 안 하고 있는데도 죽지 ??? D:\obsidian내용도 찾아보고 실제 상황을 보고 다시 확인해봐 ..코덱스 앱 서버가 죽었든지 뭐 어쨌건 뭔지 다시 클리어하고 잘 쓸 수 있게 해했

> [!question] 질문
> 지금 네가 또 계속 죽고 있는데,, 왜 병렬 처리 하지 말라고 그랬고 서브 에이전트 안 하고 있는데도 죽지 ??? D:\obsidian내용도 찾아보고 실제 상황을 보고 다시 확인해봐 ..코덱스 앱 서버가 죽었든지 뭐 어쨌건 뭔지 다시 클리어하고 잘 쓸 수 있게 해했

## 답변

**1. 결론**

확인된 종료는 하나가 아니라 두 경로다. 이번 20:38 CLI 종료는 진단 도중 실제로 `spawn_agent`가 한 번 호출된 직후 발생했다. 반면 오늘 오전의 데스크톱 앱 `app-server` 종료는 서브에이전트 없이도 발생했다. 따라서 병렬 실행은 CLI 종료의 강한 재현 트리거지만, 전체 장애의 단독 원인은 아니다. 두 사건의 공통점은 정상적인 실패 이벤트 없이 Codex 실행 계층이 사라진다는 점이다. (참고: [노트 1], [노트 2], [노트 3])

**2. 이번 CLI 종료의 원시 기록**

20:35에 시작된 부모 rollout에서 확인된 순서는 다음과 같다.

1. 20:38:41 부모 AgentMessage 완료
2. 20:38:44 `function_call: spawn_agent`
3. 20:38:45 자식 세션 생성 및 `SubAgentActivity` 완료
4. 20:38:47~51 부모의 다음 로컬 명령 실행·완료
5. 20:38:53 부모 Reasoning 완료
6. 이후 `task_complete`, 구조화된 `error`, 최종 답변 없이 rollout 단절

직후 화면은 PowerShell 프롬프트로 돌아왔다. 같은 시각 Windows Application Error/WER에는 새 `codex.exe` 크래시가 없었다. 화면에 같은 이름의 `Started`가 두 번 표시됐지만 부모 rollout의 실제 `spawn_agent` 함수 호출은 한 번이었다. (참고: [노트 1])

**3. “서브에이전트를 쓰지 않았는데도 죽는다”는 관찰도 맞는 이유**

오늘 오전 데스크톱 앱에서는 multi-agent 호출 없이도 UI 내부의 app-server 자식이 반복 종료됐다. 당시 UI 프로세스는 살아 있었지만 app-server가 사라졌고, 종료 코드는 `3221225786 = 0xC000013A`였다. Windows 크래시 이벤트, Crashpad 덤프, OOM 증거는 없었다. 따라서 이 경로는 이번 CLI의 spawn 직후 종료와 구체적인 트리거가 다르다. (참고: [노트 2], [노트 4])

**4. 현재 설정에서 다시 spawn이 가능했던 이유**

현재 전역 설정에는 `multi_agent = true`가 남아 있고 `[features.multi_agent_v2]`의 동시 스레드 상한은 5다. 여기에 병렬 가능한 작업에서 서브에이전트를 사용하라는 AGENTS 지침이 결합되어, 과거 운영상 피하기로 했어도 모델은 다시 spawn을 선택할 수 있었다. `computer-use@openai-bundled`는 비활성화돼 있지만 Browser는 활성 상태이며, `codex-computer-use.exe turn-ended` notify는 앱에 의해 자동 복원된 상태다. (참고: [노트 1], [노트 4], [노트 5])

**5. 과거 조치가 근본 해결이 아니었던 이유**

`computer-use` 플러그인 비활성화와 중복 marketplace 정리는 한때 재시작·생존 검사를 통과하게 했지만, 이후 app-server 종료가 다시 재현됐다. 앱 본체가 Computer Use 플러그인 상태와 별도로 notify와 native pipe를 유지하므로 플러그인만 끄는 조치는 원인 변수를 완전히 제거하지 못했다. 과거 Headroom·Waveterm도 제거 또는 환경 변경 뒤 재현이 이어져 단독 원인에서 제외됐다. (참고: [노트 2], [노트 3], [노트 4], [노트 5])

**6. 현재 확정·미확정 판정**

- **확정:** 이번 20:38 CLI 종료 직전에 서브에이전트가 한 번 생성됐다.
- **확정:** 부모 rollout은 정상 완료나 구조화된 오류 없이 끊겼다.
- **확정:** 같은 시각 Windows의 일반 애플리케이션 크래시 기록은 없다.
- **확정:** multi-agent는 현재 전역에서 활성화돼 있다.
- **확정:** 데스크톱 app-server는 서브에이전트 없이도 별도로 종료됐다.
- **강한 추정:** 이번 CLI 사고는 2026-07-29에 기록된 child lifecycle/부모 종료 계열과 같다.
- **미확정:** CLI 종료와 앱 `0xC000013A` 종료가 정확히 같은 Codex core 결함인지 여부
- **미확정:** notify 또는 Computer Use native pipe가 앱 종료 신호에 직접 관여하는지 여부

(참고: [노트 1], [노트 2], [노트 3], [노트 6])

**7. 안정화 순서**

1. 우선 multi-agent를 전역에서 비활성화해 가장 재현성이 높은 CLI 종료 경로를 차단한다.
2. 기존 장기 세션 resume 대신 새 단일 에이전트 CLI 세션에서 10~15분 생존 검사를 한다.
3. 데스크톱 앱은 별도 A/B 대상으로 두고, multi-agent 차단 뒤에도 app-server가 죽는지 본다.
4. 그 다음에만 Computer Use 정책과 notify/native pipe를 한 변수씩 바꿔 검사한다.
5. 인증·세션·설정 전체 삭제나 무근거 재설치는 하지 않는다. 변경 전 설정 백업과 원시 로그를 보존한다.

현재 작성된 진단 문서는 변경 제안만 기록했으며, multi-agent 비활성화나 notify 변경은 아직 적용하지 않았다. (참고: [노트 1])

**8. 상태 DB·0.147.0 소스까지 확인한 추가 결론**

사고 프로세스의 로그 1,193건과 상태 DB를 다시 대조했다. 부모와 자식은 동일한 `codex.exe` 호스트 안에서 실행됐고, 종료 뒤 두 turn 모두 `inProgress`, 오류 없음, 완료 시각 없음으로 남았다. 자식은 훅과 첫 명령을 정상 완료했으며 두 번째 모델 요청을 시작한 직후, 정상 WebSocket 이벤트를 마지막으로 호스트 전체 로그가 끊겼다. provider/API 실패, MCP 초기화 실패, notify 실행, panic·fatal·shutdown 기록은 없었다.

자식은 전역의 10개 MCP 서버와 내장 앱·플러그인·보안 서버 구성을 그대로 초기화했다. 개별 서버는 정상 로그를 남겨 특정 MCP 하나를 범인으로 확정할 수 없다. 현재 가장 좁은 원인 경계는 **Windows `MultiAgentV2` 자식 수명주기 + 자식이 상속한 대규모 MCP·플러그인·앱·훅 표면 + 부모와 자식이 공유하는 단일 호스트 프로세스**다. 이 경계에서 하드 종료가 발생해 부모까지 함께 사라진다.

`incremental request failed, items didn't match`는 Codex `0.147.0` 소스상 전체 요청으로 되돌아가는 정상 TRACE 폴백이므로 원인이 아니다. `openai/codex #36012`는 여전히 열려 있고 수정 PR도 연결돼 있지 않다. `0.147.0`의 MCP 시작 관련 변경으로 자식이 과거보다 더 진행했지만, 부모를 살려 두는 안전 경계는 해결되지 않은 것으로 판단한다. 마지막 종료 신호를 만든 단일 컴포넌트와 실제 CLI exit code만 아직 미확정이다.
