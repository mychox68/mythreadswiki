## 쟁점 1 — 객체 스토리지: S3 vs R2 vs DO Spaces

```
S3          [Client] <---- 데이터 나갈 때 $$$ egress fee ---- [S3 bucket]
R2          [Client] <---- egress 요금 없음(Cloudflare가 흡수) ---- [R2 bucket]
DO Spaces   [Client] <---- 월 $5 정액(스토리지+CDN 250GB 포함) ---- [Spaces bucket]
```

- **S3**가 "정석"인 이유: 업계 표준 API, IAM/CloudFront 등 AWS 생태계와의 깊은 통합. 대신 외부로 나가는 트래픽(egress)에 과금되는 게 약점.
- **R2**(Cloudflare)는 S3와 API 호환이면서 egress 요금이 0원 — "R2가 s3보다 개쌉니다"는 바로 이 지점을 가리킨 말.
- **DigitalOcean Spaces**는 스토리지+CDN을 월 정액으로 묶어 파는 상품이라 가격 예측이 쉬워 초심자에게 "개추"로 언급됨.

## 쟁점 2 — 프론트엔드 배포: Amplify vs Vercel/Netlify

- **AWS Amplify**는 AWS 풀스택 생태계(Cognito, AppSync 등)와 엮이는 대신, Next.js 최신 기능(App Router, 서버 액션, 엣지 런타임 등)을 [[Vercel]]보다 항상 한 세대 늦게 지원하고 빌드/배포 파이프라인도 상대적으로 느리다는 게 지적된 단점.
- **Vercel**은 Next.js를 만든 회사가 직접 운영하는 호스팅이라 신기능이 나오는 즉시 지원됨. **Netlify**도 유사한 Jamstack 전문 호스팅으로 배포 속도가 빠름.
- → "프론트는 그냥 프레임워크 제작사/전문 호스팅에 맡기고, AWS 락인은 백엔드에서만 가져가라"는 실용적 결론.

## 쟁점 3 — 백엔드: Elastic Beanstalk vs Lightsail vs Supabase

- **Elastic Beanstalk**: EC2+오토스케일링+로드밸런서를 자동으로 구성해주는 AWS의 PaaS. 서버를 직접 만지지 않고 코드만 올리면 배포되지만, 여전히 "AWS 안에서" RDS(관리형 DB)·S3(스토리지)를 붙여가며 운영 감각을 익힐 수 있음. 카놋사의굴욕이 "한 달 5만원 쓸 용기"라고 표현한 건 EC2+RDS+S3를 합친 대략적인 월 비용.
- **[[Supabase]]**: Postgres+Auth+Storage+Realtime을 통째로 제공하는 BaaS. 백엔드 코드를 거의 짜지 않아도 되는 대신, 커스텀 소켓/복잡한 서버 로직이 필요해지면 한계에 부딪힘 — "사실상 프론트만 공부하게 될 것"이라는 우려는 백엔드 운영 학습 기회 자체가 줄어든다는 뜻.
- **Lightsail**: AWS판 단순 VPS(DigitalOcean Droplet과 같은 포지션). 소확행은 Lightsail(서버) + Supabase(DB/Auth) 조합을 실전에서 사용 중이며, "완벽히 따라가려 하지 말고 일단 만들고 터지는 부분을 고치는" 실용주의를 강조.

## 용어 정리

| 용어         | 의미                                                                    |
| ---------- | --------------------------------------------------------------------- |
| PaaS       | 서버 프로비저닝·스케일링은 플랫폼이 담당, 개발자는 코드 배포만 (Elastic Beanstalk, Heroku 등)     |
| BaaS       | DB·인증·스토리지 등 백엔드 기능 자체를 통째로 제공 (Supabase, Firebase)                   |
| Egress fee | 클라우드에서 외부로 데이터가 나갈 때 부과되는 트래픽 비용. S3의 대표적 약점, R2/Cloudflare는 이 요금이 없음 |
| VPS        | 가상 사설 서버 — OS·런타임을 직접 관리 (Lightsail, DigitalOcean Droplet)            |
| RDS        | AWS의 관리형 관계형 DB 서비스 (백업·패치·복제를 AWS가 대행)                               |

## 왜 중요한가 (배운 점)

- 클라우드 스토리지·호스팅 선택은 "정석"과 "비용/편의" 사이의 트레이드오프이며, 실제로는 용도(egress 많은 서비스인지, Next.js 최신 기능이 필요한지, 커스텀 백엔드 로직이 필요한지)에 따라 답이 달라진다.
- 초심자에게 반복되는 조언은 "완벽한 스택 선택"이 아니라 **"끝까지 한 바퀴 도는 걸 먼저 만드는 것"** — 완주 경험이 있어야 이후 최적화·교체가 의미를 가진다.
- 나중에 실제로 배포를 결정할 때, 이 문서의 두 갈래 스택(A: AWS 완주 / B: Supabase 간편)을 참고해 상황에 맞는 쪽을 고른다.
